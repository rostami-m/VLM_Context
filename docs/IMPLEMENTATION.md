# Implementation provenance and boundaries

The release separates numerical/model kernels from portable execution commands. `docs/code_provenance.json`, `provenance/root_kernel_extraction.json`, and `docs/native_code_provenance.json` identify the archived producer files, their SHA256 digests, and extracted definitions. The numeric artifacts have a separate complete source/export ledger in `data/PROVENANCE.json`.

The shared Qwen scorer preserves native message rendering, complete-label-plus-one-EOS candidate spans, cached inference, independent full-forward and stepwise checks, and greedy generation validation. The explicit renderer additionally carries the declared support labels and support order for mapping/corruption controls. Strict generation parsing, the historical substring diagnostic, and sum/mean sequence scores remain distinct measurements.

The LoRA loss-input/mask functions, named target inventories, mixed-rank recipes and injection checks are extracted from the accepted code. `adaptation.fit` is a portable training loop around those kernels: it removes host/deadline/approval dependencies, reads the frozen episode schedules, applies the same AdamW updates, records the causal-loss comparison and finite gradient/update checks, and verifies that frozen parameter bytes remain unchanged. Training commands write the runtime, target ledger, recipe, schedule digest, per-step evidence, final checkpoint and checkpoint hashes. Evaluation checks the completed fit's arm, task, seed and file hashes. A technical smoke checkpoint cannot be used as a full evaluation checkpoint.

The exact seed/version strings used by the archived scientific protocol are retained, including date-like strings. They are inputs to deterministic hashes and must not be renamed when changing documentation or directory layout. Absolute machine paths, launch deadlines, remote-machine locks, approval receipts, and historical API model entrypoints are not part of the portable execution contract.

DARA factor updates and attention intervention semantics are extracted separately. The feature comparator uses the final FP32 postmerger path. The earlier order-only experiment retains its original BF16 path, while later mechanism/Gate/Inject inference uses BF16-loaded values promoted to FP32. The continual study and controller have their own documented precision phases. These choices should not be flattened into one global dtype setting.

Portable wrappers intentionally require fresh result directories. They do not attempt to resume partial optimizer state or silently substitute a model, dataset, prompt, fitting seed, or checkpoint. Model licenses and source-dataset terms continue to apply; no image bank or pretrained/adapted weights are redistributed in the repository.

CPU tests validate score reduction, invalid-answer denominators, full-answer supervision, disjoint splits, mapping/order invariants, target budgets, calibration domains, policy rules, and archived numeric reductions. Small native checks are recorded separately in the release validation report. They do not establish that the complete training/inference grid was rerun on the release machine, nor do they guarantee bitwise agreement across hardware or package versions.
